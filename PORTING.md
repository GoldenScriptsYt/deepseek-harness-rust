# Rust port plan

Goal: replace the Node Host with a Rust Host behind the same wire protocol, shipped inside the Tauri carrier (`apps/desktop-tauri`). The TypeScript tree stays authoritative until a Rust crate passes the same recorded fixtures.

## Method

- One Rust crate per TypeScript package, named `dsh-<package>`, under `rust/crates/`.
- A crate is done when it passes the recorded corpus in `snapshots/` or an equivalent fixture set, not when it compiles.
- The web client (`packages/client/*`, `apps/web`) stays TypeScript and runs in the webview. The Rust Host serves it and speaks the `/api/remote.mux` protocol described in `packages/api/gateway/README.md`.
- The Python and TypeScript SDK expected outputs are the end-to-end gate (`pnpm run test:snapshot`).

## How the remaining web API is ported

The Rust Host logs every RPC and stream the web client calls that it does not answer yet (`[dsh-rs] unported rpc: ...`). To port one:

1. `rust/tools/restart_host.ps1` rebuilds and starts `dsh-rs web` on port 3192; open its printed URL in a browser. The log is `$env:TEMP\dsh-rs-web.err`.
2. Start the TypeScript Host as the reference (`node --import tsx/esm apps/cli/src/bin.ts web --no-open --port 3191`, own `DSH_HOME`), sign in with `curl -c`.
3. `rust/tools/capture_rpc.py <method> '<payload>'` stores its answer in `crates/dsh-cli/assets/rpc/`; `rust/tools/capture_streams.mjs` records stream frames (run it while triggering the change with curl).
4. Static answers register from the fixtures in `crates/dsh-cli/src/api.rs`; answers that depend on Host state are implemented in Rust and unit-tested against the captured shape. `crates/dsh-cli/assets/rpc/session_create.json` is registered.

Browser automation against the client is unreliable in this environment; `rust/tools/follow_probe.mjs <cookie> <sessionId> [endpoint]` drives one stream over the real mux and prints every frame, which is how the opening snapshot and the populated history were verified.

Not yet ported from the web API: live increments on the remaining boot streams, authenticated attachment upload and receipt lifecycle, workspace/file and terminal/job startup integration, plugin installation and runtime, account notifications and server-side logout revocation, remote connections.

Migrations v0-v3 are deferred with evidence: every Session on the development machine is v4 (80 of 80 current-generation logs), the recorded corpus is v4, and each frozen edge is tested in TypeScript against inline objects rather than data files, so a Rust port has no oracle. Open an older Session once through the Node Host, which rewrites it as v4, before switching.

## Open decisions

- **Cordis plugin model (decided).** Native Rust: a typed event bus with ordered listeners, waterfall `next()` delegation and scoped disposal, replacing `ctx.effect()` / `ctx.on()`. No embedded JS runtime.
- **Plugin ecosystem.** Bundle listing and startup registration have tested Rust modules. Installation, the plugin market, updates, and user-installed TypeScript plugins are not ported. Full coverage includes `boot/plugin-manager`, `plugin-market`, and `extensions/*`, which needs a decision about running or refusing TypeScript plugins inside a Rust Host.
- **Experimental packages** (`packages/experimental/*`, about 100k lines) are in scope for full coverage, last in order behind the product path.
